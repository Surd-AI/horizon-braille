# Private backend corpus audit

## Visible results take priority

Unsupported commands keep their readable control-word spelling and arguments while surrounding supported expressions continue to convert. Unsupported environments retain their named literal source bodies. These fallback fields remain marked for review and are not silently assigned mathematical meaning. Formatting-only nonempty fields retain labelled literal source rather than producing a blank result. Known `nobreak` / `allowbreak` hints are adapted to Braille layout without deleting neighboring formula content.

The existing editor displays partial Unicode/ASCII output and an unpaged preview when strict line layout fails. A failed or hung worker falls back to local conversion; a local conversion exception exposes a labelled literal-source result. Source text remains editable, and source-bound Chinese word edits leave generated explanatory captions intact.

The latest full corpus replay includes 115 Devanagari character identities, after whole-word readings and earlier fixes. All 3,815 core tests across 130 files pass. Actual editor acceptance covers character/vowel-sign descriptions, aligned Chinese, manual word edits and visible unknown input. The independent ESM/CommonJS package passes (144 files), with fourteen additional Node runtime fixtures including inherited fonts. The authentic 100,000-input replay has zero exceptions, empty results, source changes, invalid spans or preview truncation; 80,160 inputs are complete and 19,840 remain visibly reviewable. Compared with the preceding engine, 3 additional inputs complete and none newly become partial. Complete counts include readable editorial descriptions, not only native point signs. Earlier stages retain their own hashes and verification scopes.

The audit accepts up to 100,000 unique inputs from a private, read-only backend export. Customer inputs must remain outside Git. Publish only aggregate reports. Deduplicate the extracted source, not its storage wrapper; the backend `mix_doc` field contains JSON with a `markdown` string.

Each sample has `source` and an optional `format` (`latex` or `markdown`). Legacy exports without a format are treated as LaTeX. Backend identifiers, image paths, request identifiers and account identifiers are not needed and must not be exported. LaTeX sources are bounded at 5,000 UTF-16 code units; Markdown at 20,000. Export files are bounded at 256 MiB.

Build the current browser core before auditing:

```powershell
npm run horizon:core:build
node horizon/scripts/audit-backend-corpus.mjs PRIVATE_INPUT.json AGGREGATE_REPORT.json
```

An optional third argument saves failed samples privately for investigation. Never place this file in the repository or attach it to a published report.

LaTeX is tested in explicit math mode. Markdown is tested in document mode, matching mixed-input detection. This is a test of the actual existing converter, not a claim that every Markdown structure is implemented. Reports separate these modes and record overlapping Markdown features (headings, lists, tables, links, images, code, math delimiters, Chinese and multiple lines).

The report includes the exact browser engine hash, processing duration, complete/partial counts, exceptions, empty results, display-only previews, source changes, document-span failures, out-of-bounds atom/diagnostic spans, unresolved-span failures, truncation and diagnostic counts. Exceptions do not terminate the entire batch: they count as partial and exceptions. A nonzero exit indicates a preservation, span, exception or truncation defect. Ordinary unresolved conversion cases remain partial even when the preservation audit succeeds.

Complete conversion counts are not independently verified braille accuracy, standards certification, or evidence that every piece of Markdown structure retained its meaning. Inspect representative rendered output and rule-level fixtures before treating a new syntax family as supported. Generated or transformed test cases must be counted separately from authentic backend samples.

`fontDescriptionInputs`, `fontDescriptionFields` and `completeWithFontDescriptions` separately identify visible editorial font-name transcriptions. These preserve the named font and complete body without inventing a native GB font sign. They are included in renderable complete counts but must not be reported as newly verified native font indicators. The `review-unmapped` core option remains available for manual-review workflows.

`symbolDescriptionInputs`, `symbolDescriptionFields` and `completeWithSymbolDescriptions` separately identify editorial semantic symbol descriptions. Font and symbol categories can overlap and must not be added as disjoint totals. The `review-unmapped` symbol policy keeps absent native signs flagged for manual review.

`literalGlyphDescriptionInputs`, `literalGlyphDescriptionFields` and `completeWithLiteralGlyphDescriptions` separately count editorial Latin diacritic/nondecomposable letter identity, numeric glyph, Unicode layout-space, Arabic/Devanagari character, Cyrillic letter/ligature and declared Greek-form descriptions. These identify source glyphs or declared form names and preserve case, value or marks without asserting a new native glyph-specific braille profile. Categories can overlap with font and mathematical symbol descriptions. Older reports omit these counters; omission is not evidence of zero descriptions.
